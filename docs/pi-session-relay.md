# Pi 会话接力

接力将一个正在运行的 Pi TUI 会话绑定到一个飞书话题。飞书输入由该终端进程执行；TUI 显示用户消息、模型回复和工具执行，话题里只有本机输入镜像和每轮的正式回复。多个终端会话分别绑定不同话题，不共享“当前会话”指针。

## 前提

- 使用 Pi TUI 和持久会话；print、JSON、RPC 模式及内存会话不支持绑定。
- 使用已配置机器人且机器人可以发言的话题群。授权账号必须是群主的 `open_id`，不能填 `user_id` 或 `union_id`。
- 机器人需要已有的群信息读取和消息发送权限。无需 @ 的话题输入仍需要飞书后台授权机器人接收群内所有消息；扩展无法绕过飞书平台权限。
- 飞书网关和终端在同一台机器、同一操作系统账号下。接力不提供跨机器网络入口。
- 飞书用户拥有与本机 Pi 相同的工具能力；本机工具确认机制继续生效，需交互确认的操作可能仍需回终端处理。

## 安装与配置

此分支可通过 Git 安装，不要与旧的 `pi-feishu-lark` 或另一份 `ax-feishu-bridge` 同时加载：

```bash
pi install git:github.com/yuhaoxin/ax-feishu-bridge@feat/feishu-session-handoff
```

替换已有安装前先停止旧网关并备份配置。Pi 适配器使用 `~/.pi/agent/feishu/config.pi.json`、`state.pi.json`、`bridge.pi.json`；旧版的 `config.json`、`state.json`、`bridge.json` 不会自动迁移。可重新运行 `/feishu setup`；需要保留原映射时，在网关停止后备份并迁移对应文件，不覆盖已存在的新配置。恢复旧历史不等于建立接力绑定。

在终端中执行：

```text
/feishu start
/feishu relay setup oc_目标话题群 ou_你的账号
```

`setup` 读取群信息验证话题群及群主，不发送消息，并开启「新会话自动绑定」（默认开，可用 `/feishu relay autobind on|off` 切换）。此后每个新开的 Pi TUI 会话在你敲下第一条输入时自动创建一个独立话题。标题为「工作目录最后一级:首条输入前 30 字」加会话短 ID，其中工作目录名截 20 字、首条输入截 30 字；会话被显式命名过（`/name`、`-n`）时用会话名替换首条输入。之后在 Pi 里改名（`session_info_changed`）会按同一规则重拼标题，名字清空则回退到首条输入。来自 RPC 或其它扩展注入的消息不算用户输入，既不建话题也不镜像。没有实际输入过的会话不会创建话题。

接力配置只可通过终端命令设置，模型工具不能改变群或授权账号。已有话题后不允许更换目标群或账号，避免旧话题和权限发生歧义。

## 日常操作

```text
/feishu relay status
/feishu relay echo on|off
/feishu relay exit-notice on|off
/feishu relay push 指定通知内容
/feishu relay unbind
```

模型可调用 `feishu_relay` 工具的 `status`、`push`、`unbind`、`autobind` 操作。显式推送应由用户明确要求。工具没有任意收件人参数，仅操作当前会话，也不能改变群、授权账号、输入镜像或退出通知开关。

本地输入镜像默认开启：你在终端里敲的每条输入都会以 `🖥 输入：` 前缀发到话题，与模型回复一起构成完整的对话记录；只有图片没有文字时用 `[图片 ×N]` 占位。`/feishu relay echo off` 关闭后话题只收正式回复，重新打开不补推关闭期间的输入。扩展命令（如 `/feishu relay ...`）由 Pi 在输入事件之前拦截，不会进入话题；`/skill:` 与模板会被镜像为输入原文。飞书发来的消息在飞书侧本来就可见，不会回显。

- 在绑定话题回复文本即可继续操作对应终端，无需在多个会话间执行 `/resume`。
- TUI 忙时使用 Pi 的 `steer` 队列，在工具执行边界引导当前任务，不强制中止运行中的工具。
- TUI 关闭、切换会话或接力断联时不交给后台接管；离线输入不排队、不自动重放。
- 正常退出 TUI（Ctrl+C、Ctrl+D、`/quit`，以及 SIGTERM/SIGHUP 触发的关闭）时向绑定话题推送一条「对话已关闭」提示，默认开，`/feishu relay exit-notice off` 关闭。切换会话（`/new`、`/resume`、`/fork`）、`/reload`、终端消失或进程被强杀都不推送；网关未运行或话题已解绑时发不出。推送超过 1.5 秒等待上限时终端不再等待，消息可能已送达也可能没有。
- 同一会话重新打开后自动恢复连接和绑定。断线期间的输出不自动补发，需要时显式推送。
- 同一会话不能由两个 TUI 接力连接同时占用。已由普通飞书后台加载的会话不能接力注册；先在飞书切换到新会话并重启网关。
- 接力管理的会话不能再从普通飞书 `/resume` 路径驱动后台模型，避免两处写入同一历史。
- `unbind` = 本会话永久退出接力：解绑并记入退出名单，此后 `session_start` 不再自动绑定；旧话题继续拒绝执行。退出后想恢复只能删除会话重新打开（新会话 ID 会自动绑定）。`autobind off` 是全局开关，关闭后新会话都不建话题，已绑定的会话不受影响。
- 接力话题目前只接收文本（含纯文本富文本消息），不下载图片、文件或展开引用附件。斜杠命令作为普通输入送入 Pi，不执行飞书的 `/resume` 等后台管理命令。
- 普通、未绑定的飞书会话保持原有后台聊天行为；本功能的单账号限制只保护接力话题，不改变其他会话的访问策略。

## omp 差异

omp 复用同一份接力实现，data 目录、锁与日志都在 `~/.omp/agent` 下，与 Pi 完全隔离。行为差异都来自宿主事件面不同：

- **会话切换事件**：omp 在进程内切换会话（`/new`、`/resume`、`/fork`）只发 `session_switch`，不发 `session_start`；pi 走 `session_start` 的 `reason`。两条路径都重新接线：切到哪个会话就跟到哪个会话，该会话有历史绑定就复用原话题，没有就在下一条真实输入时建新话题。切走时旧会话的连接当场释放，旧话题里再发消息会收到「绑定的 Pi TUI 已离线」。
- **进程内 resume 与 reload**：omp 上没有 `/reload` 命令，`/reload-plugins` 也不触发接力事件；扩展自己调用的 `ctx.reload()` 表现为 `session_switch` + `reason=resume`，会话 id 不变，此时沿用现有连接，不会重连掉线。
- **退出通知**：omp 的 `session_start`/`session_shutdown` 没有 `reason` 字段，且只在进程退出时发 `session_shutdown`，因此收到即视为退出；pi 的两个事件都带 `reason`，切会话（`new`/`resume`/`fork`）与 `reload` 复用同一事件，只有 `reason=quit` 才推关闭提示。
- **会话改名**：omp 没有 `session_info_changed` 事件，话题标题只在建话题时按「目录名:会话名或首条输入」定型，之后改名不同步。
- **斜杠命令**：omp 把宿主命令（内建 `/new`、扩展 `/feishu ...`）也当作终端输入送进 `input` 事件，而 pi 在输入事件之前就拦截。命令不建话题也不镜像，避免话题里出现命令行文本；`/skill:` 与模板仍按输入原文镜像。

## 正式回复

每条正常完成且不含工具调用的助手消息都会即时同步到话题，而不只是最后一轮：思考块、工具参数、工具结果、失败或取消的草稿、流式中间内容都不发送。支持阶段标记的模型只保留 `final_answer`，过滤 `commentary`。同一轮里模型给出多条正式答案时按顺序各发一张卡片。整轮没有正式答案（被中止、出错或只跑工具）时，话题里会收到一条纯文本说明，不会静默。

飞书不显示生成中的流式卡片。正式答案分块发送到同一话题，保留完整内容（单条答案最多 200000 字符，超限会在终端提示，不静默截断）。主动推送的单次文本最多 100000 字符。离线、忙时送达及投递不确定等必要状态提示不属于模型输出，仍会显示。

出站消息按输入顺序串行发送，所以话题内的顺序与终端一致。推送失败不重试：网关或网络不可用时话题里会缺少对应内容，终端提示首次错误，连续 3 次失败合并为一条提示，任意一次推送成功后恢复逐条提示。断连或切换会话时排队中未发出的消息被丢弃，不补发。

不支持 cron 或关闭终端后执行任务。这里的任务结果推送就是活跃 TUI 完成一轮后的正式回复同步。

## ask 提问

接力绑定的会话里，`ask` 工具由扩展接管：同一个问题同时发到绑定话题的交互卡片和终端对话框，任一侧先作答即返回，另一侧自动收起。未绑定的会话保持原样，交给宿主原生 `ask`；只有接力绑定的那个会话被接管，子 agent 等其它会话仍是原生行为。

飞书卡片用 interactive 1.0 格式（只有 1.0 静态卡能原地刷新，混用 CardKit 2.0 会被飞书判为版本不匹配）：

- 单选问题渲染成选项按钮，点按即作答，推荐项在按钮上标 `(推荐)`；选项超过 5 个时降级成编号列表，在话题里回复编号或文字即算作答。
- 多选问题点按钮切换选中态（按钮前缀 `✅`），选中至少一项后出现「提交」，点提交才算答完。
- 「✏️ 其他」把该问题置为等待文本，你在话题里回复的文字就是答案；「📝 补充说明」同样等一条文本，作为该问题的备注。这两段文本只回到提问结果里，不会作为 steer 送进会话。
- 一张卡片可承载多个问题，逐条作答、卡片随手刷新已答状态，全部答完才算完成。

提问没有等待上限：只有用户作答、终端连接断开或会话切换才结束，不会替用户选一个答案。催单来自飞书配置 `askNotifySec`（秒，默认 0 即不催单）：在配置文件里写，或经 `OMPFEISHU_ASK_NOTIFY_SEC`（pi 侧前缀为 `FEISHU_`）与 `/config` 设置；到点在话题里提醒一次，不改变卡片状态。终端 `ask.timeout` 属于宿主设置，扩展读不到，也不参与飞书侧的等待策略。

结果以普通工具结果返回，文本与 `details` 与原生 `ask` 同构（单问题扁平字段、多问题 `results` 数组，含 `selectedOptions`、`customInput`、`note`），模型不需要区分答案来自哪一侧。

生命周期：终端连接断开（进程退出、切换会话、接力离线）时等待中的提问立即结束，卡片标为「已结束」；提问已结束时再点旧卡片只会原地刷新成「已结束」，不会把上一轮的答案写进新一轮。终端先作答则卡片标「已在终端回答」，终端侧超时收尾则标「超时自动作答」。

扩展在 TUI 进程启动时加载，omp 没有 `/reload`：升级插件后需要重开 TUI 会话才会接管 `ask`，已在运行的旧会话继续使用原生 `ask`。

## 安全与故障

网关只监听 `127.0.0.1` 随机端口，以每次启动重新生成的随机令牌校验本机连接。令牌文件为当前用户可读写的 `0600` 文件；同一操作系统账号下的进程属于同一信任边界，不防御该账号内的恶意进程。

| 文件 | 内容 |
| --- | --- |
| `~/.pi/agent/feishu/relay-state.pi.json` | 机器人 ID、授权账号、绑定（含解绑记录）、投递记录 |
| `~/.pi/agent/feishu/relay-endpoint.pi.json` | 网关本机端口和随机令牌，不应分享或提交 |
| `~/.omp/agent/feishu/relay-state.omp.json` | omp 侧的同一份接力状态 |
| `~/.omp/agent/feishu/relay-endpoint.omp.json` | omp 侧的网关端口与令牌 |

入站消息先记录再注入，故障后不会重试可能已执行过的指令。投递确认仅表示终端调用了消息注入接口，不表示模型或工具已完成。断联、超时或失败时可能已接收或部分发送，需要检查终端/飞书后再决定是否重发；不宣称“恰好执行一次”。

话题创建前持久化 `pendingTopic`。若创建接口超时或创建后的状态落盘失败，无法确定是否留下孤立话题，网关会暂停新建及目标群的普通后台分派，已有绑定话题仍按原路由处理。恢复步骤：停止网关，备份接力状态；在飞书确认并删除或明确弃用孤立话题后，移除状态中的 `pendingTopic` 再启动。不要仅清空整个状态文件，否则旧接力话题可能回落到普通后台会话。

`/feishu reset` 保留接力状态。更换机器人前需要单独规划旧话题清理和状态迁移；机器人 ID 不匹配时网关拒绝启动接力，不能使用其他机器人的绑定。

```bash
npm ci

```

上游测试脚本使用 `--experimental-transform-types`，请用 Node 24 运行（`npx -y node@24 ...`）；Node 26 已删除该参数。用 Bun 跑可以做粗筛，但 `test/gateway-lock.test.ts` 会因 Bun 在进程启动时缓存 `homedir()`（运行时改 `process.env.HOME` 不生效）出现一项假失败。测试覆盖真实环回 TCP、多会话隔离、账号校验、去重、离线和解绑拒绝、重连、正式回复过滤，以及真实 Pi SDK 配合本地模型 HTTP 替身的端到端处理。测试不使用生产机器人凭证，也不向飞书外发。
